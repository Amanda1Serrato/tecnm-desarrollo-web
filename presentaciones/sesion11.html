Arquitectura en Capas: Router, Servicio y Capa de Datos

Sesión 11 del curso. Arquitectura en capas, gestión de dependencias, seguridad criptográfica y control de acceso con la Tríada Metodológica.

01. El Artesano[+]

Codificación manual sin IA para experimentar el diseño de controladores desacoplados y hashing.

Desarrolla la intuición técnica de capas de servicio, salting y validación de tokens.
02. El Científico[+]

Especificación formal C-R-E-O para flujos de autenticación OAuth2 y esquemas de roles RBAC.

Define contratos de seguridad con claims JWT y códigos de respuesta semánticos (401, 403, 429).
03. El Auditor[+]

Test Harness automatizado con pruebas de intrusión, tokens manipulados y expirados.

Auditoría destructiva sobre rutas protegidas y verificación de permisos en GitHub.

00–20 min: Fundamentos Teóricos — Separación de Responsabilidades y Patrón Service Layer

El desacoplamiento en capas aísla la capa de transporte HTTP de las reglas del negocio y el acceso a la base de datos.

01. Capa de Rutas / Controladores[+]

Recibe la petición HTTP, valida el esquema DTO de entrada y delega la ejecución al servicio.

No debe contener lógica de negocio ni sentencias SQL directas.
02. Capa de Servicio (Service Layer)[+]

Orquesta las reglas de negocio puras, cálculos de dominio y validaciones complejas.

Es independiente del framework web; puede reutilizarse en scripts CLI, tareas en background o gRPC.
03. Capa de Acceso a Datos (Repository / DAO)[+]

Encapsula las operaciones de persistencia (ORM / SQL) y transacciones.

Permite cambiar el motor de base de datos sin alterar la lógica de negocio.
Invariante de Seguridad: La autenticación verifica la identidad; la autorización delimita estrictamente los privilegios sobre cada recurso.

Arquitectura del Servidor y Seguridad: Flujo Unidireccional de Datos en Memoria

Ciclo de vida de los objetos a través de las capas de la aplicación:

Transformación DTO -> Entidad -> DTO[+]

El Router pasa DTOs al Servicio; el Servicio opera con Entidades de Dominio y devuelve DTOs de salida.

Previene la fuga accidental de modelos internos o contraseñas al cliente.
Aislamiento de Pruebas Unitarias[+]

Permite mockear la capa de datos en memoria para probar las reglas de negocio en milisegundos sin tocar la base de datos.

Aumenta la cobertura y velocidad del pipeline CI/CD.

Antipatrones en Arquitectura en Capas

Puntos críticos de falla y vulnerabilidades que deben protegerse en la implementación y auditarse en la IA:

  • Controladores 'Gordos' (*Fat Controllers*) con cientos de líneas mezclando parsing HTTP, SQL y lógica de negocio.
  • Saltarse la capa de servicio invocando consultas de base de datos directamente desde los endpoints.
  • Dependencia circular entre servicios al no definir interfaces o contratos claros.
